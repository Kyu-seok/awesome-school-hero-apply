# AI 활용 내역

이 과제는 Claude Code(Anthropic의 CLI 코딩 에이전트)와 함께 만들었다. 이 문서는 어느 단계에서 AI를 어떻게 썼는지, 무엇을 사람이 결정했고 무엇을 AI가 했는지, AI가 만든 결과물을 어떻게 검증했는지를 적는다.

## 사용 도구

- **Claude Code**: 조사, 설계 인터뷰 진행, 문서 초안, 구현, 테스트, 코드 리뷰, 배포 스크립트까지 전 과정에 썼다.
- **GitHub Issues**: 스펙(#1)과 작업 티켓(#2~#11)을 이슈로 두고, AI와 사람이 같은 이슈를 보며 일했다. 티켓에는 `ready-for-agent`(AI가 맡음)와 `ready-for-human`(사람이 해야 함) 라벨을 붙였다.
- **GitHub Actions**: 푸시마다 `ruff check`와 `pytest`를 돌려 AI가 만든 코드를 사람 손을 거치지 않고도 계속 검사했다.

## 단계별 활용

### 1. 사이트 조사

Claude Code가 실제 히어로스쿨 사이트를 조사했다(이 저장소의 데모 서비스는 챔피언스쿨이라는 이름을 쓰며, 실제 히어로스쿨과는 별개다). 교육이 어떻게 소개되고, 누가 어떤 경로로 신청하고, 신청 뒤에 무슨 일이 일어나는지를 정리했다. 이 조사에서 "학교·기관 담당자가 수업 희망일을 골라 문의하면 담당자가 연락해 일정을 확정한다"는 흐름과 "수업 희망일은 최소 3주 뒤" 같은 운영 규칙을 찾았다.

### 2. 설계 인터뷰

Claude Code가 질문을 던지고 사람이 답하는 방식으로 설계를 좁혔다. 누가 신청하는지, 신청 하나가 무엇을 뜻하는지, "연락 가능 날짜"가 무엇인지, 상태는 몇 개인지 같은 질문에 하나씩 답하면서 모호한 부분을 없앴다.

### 3. 용어집과 ADR

인터뷰 결과를 Claude Code가 [`GLOSSARY.md`](../GLOSSARY.md)와 [ADR 0001](adr/0001-model-applications-as-b2b-org-requests.md)로 정리했다. 용어집에는 쓰지 말아야 할 말(예: 신청을 "예약"이나 "견적 요청"으로 부르지 않음)도 함께 적었다. 이후 코드, 화면 문구, 메일, 문서가 모두 이 용어를 따른다.

### 4. 스펙과 티켓

Claude Code가 [스펙 이슈 #1](https://github.com/Kyu-seok/awesome-school-hero-apply/issues/1)(사용자 스토리 47개, 구현 결정, 테스트 결정, 범위 밖 항목)을 쓰고, 이를 의존 관계가 있는 티켓 10개(#2~#11)로 나눴다. 사람이 직접 해야 하는 일(미니 PC 배포, 도메인 연결)은 별도 티켓(#9, `ready-for-human`)으로 분리했다.

### 5. 구현과 테스트

- 티켓마다 별도 브랜치와 git worktree를 만들고, Claude Code의 하위 에이전트가 티켓 하나씩 맡아 구현했다. 서로 의존하지 않는 티켓은 동시에 진행했다.
- 하위 에이전트는 테스트를 먼저 쓰는 TDD로 구현했다. 테스트는 스펙의 테스트 결정대로 HTTP 경계에서만 쓰고 내부 함수를 직접 테스트하지 않았다.
- 완료된 티켓은 통합 브랜치에 합치고, 무엇을 만들었고 무엇이 남았는지를 스펙 이슈의 진행 기록(merge log)에 남겼다. 다음 티켓의 에이전트는 이 기록과 공용 메모(규칙, 배포 구성)를 읽고 시작했다.

### 6. 코드 리뷰와 수정

구현이 끝난 뒤 Claude Code가 두 축으로 리뷰했다.

- **Standards**: 저장소의 규칙(용어집, 설정 방식, 테스트 방식)을 지키는가
- **Spec**: 스펙과 티켓이 요구한 동작과 맞는가

리뷰에서 나온 항목 가운데 사람이 고칠 것과 남길 것을 정했고, Claude Code가 고쳤다. 고친 것은 gunicorn 프로세스 사이에 공유되지 않던 throttle 기록(Redis 캐시로 이동), 배포에서 시트 설정이 빠졌을 때 조용히 넘어가던 문제(운영자에게 알림), 내보내기 결과를 관리자 페이지에 표시, 중복된 규칙과 코드 정리 등이다.

### 7. 배포

Claude Code가 배포 구성(`compose.prod.yaml`, nginx 설정, 비root Docker 이미지, `deploy.sh`)과 Google 서비스 계정 설정을 안내하는 대화형 스크립트(`scripts/setup-google-sheets.sh`)를 만들었다. 실제 배포 중 sudo가 필요한 작업과 외부 계정 작업은 사람이 했다(아래 표).

## 사람이 결정한 것과 AI가 한 것

| 사람이 결정·수행 | Claude Code가 수행 |
| --- | --- |
| 신청을 기관(B2B) 단위 요청으로 모델링(ADR 0001) | 실제 사이트 조사, B2B·B2C 두 선택지와 근거 정리 |
| "연락 가능 날짜 기준 자동 안내 메일"을 "운영자 전화 전에 메일로 먼저 연락을 연다"로 해석 | 설계 인터뷰 진행, 용어집·ADR 초안 |
| 기술 스택(Django, DRF, Celery, PostgreSQL, Redis)과 배포 대상(미니 PC + Cloudflare Tunnel) | 스펙과 티켓 작성, 티켓 간 의존 관계 정리 |
| 리뷰 결정: 신청자가 읽는 글에서는 운영자를 "담당자"라고 부른다 | 티켓별 구현(하위 에이전트, TDD), 통합 브랜치 병합 |
| 리뷰 결정: 연락일 안내 메일이 실패하면 그날 안에서만 다시 보낸다(09~17시 매시) | 두 축 코드 리뷰와 수정 |
| 리뷰 결정: 고치지 않고 남길 항목(최소 한 번 발송, 콘텐츠 출처) | 배포 구성, `deploy.sh`, 시트 설정 안내 스크립트 |
| Gmail 앱 비밀번호 발급, Google 서비스 계정 생성과 시트 공유 | 제출 문서 초안(README, 이 문서, AWS 배포 계획) |
| 미니 PC에서 `.env` 작성, cloudflared ingress 추가(sudo), DNS 레코드 추가, 배포 실행 | |

정리하면, 무엇을 만들지와 어디까지 할지는 사람이 정했고, AI는 그 결정을 위한 재료(조사, 선택지, 근거)를 모으고 결정된 것을 문서·코드·테스트로 옮겼다.

## AI 결과물 검증 방법

- **테스트**: 테스트 102개가 HTTP 응답, DB 상태, 발송된 메일, 시트에 쓰인 행처럼 바깥에서 보이는 동작을 확인한다. 날짜 규칙은 `time-machine`으로 날짜를 고정해 경계값(3주, 평일, 연락 가능 날짜 범위)을 확인한다. 내부 구현을 테스트하지 않으므로 AI가 구현을 바꿔도 테스트가 동작을 붙잡는다.
- **CI**: GitHub Actions에서 PostgreSQL 16 컨테이너를 띄우고 `ruff check`와 `pytest`를 돌린다. 티켓을 병합하기 전에는 같은 검사를 로컬에서 통과시켰고, `main`의 CI는 초록이다.
- **두 축 코드 리뷰**: 구현한 에이전트와 다른 리뷰 에이전트가 규칙 준수(Standards)와 스펙 일치(Spec)를 따로 봤다. 결과를 사람이 읽고 고칠 항목을 골랐다.
- **배포 후 수동 점검**: 자동 테스트 밖에 있는 실제 Gmail, Google API, nginx, Cloudflare는 배포한 서비스에서 직접 확인했다. 랜딩 페이지와 정적 파일, `/api/docs/`, 없는 경로의 404, 실제 신청과 접수 확인 메일 수신, 데모 운영자 로그인(`/admin/`은 거부), 시트 내보내기를 점검했고, 점검용 신청은 취소 상태로 바꿔 두었다.
- **제출 전 점검**: README의 로컬 실행 절차를 새로 clone한 저장소에서 그대로 따라 해 보고, README의 링크와 저장소에 비밀 정보가 없는지 확인했다.

## 실제 사례: B2C에서 B2B로 방향을 바꾼 과정

과제 문구는 "교육 신청"이다. 이 문구만 보면 학생이나 보호자가 교육 기수에 등록하는 B2C 흐름으로 읽힌다. 그렇게 만들었다면 기수, 정원, 모집 기간이 핵심 모델이 되고, 만 14세 미만 아동의 정보를 다루므로 법정대리인 동의도 필요했다.

Claude Code가 실제 히어로스쿨 사이트를 조사해 보니 흐름이 달랐다. 학교·기관 담당자가 교육과 수업 희망일을 골라 문의하고, 담당자가 연락해 일정을 확정한다. 수업은 학교마다 따로 잡히므로 기수나 정원이 없다.

Claude Code는 두 선택지(보호자가 기수에 신청하는 B2C, 기관이 수업 희망일에 신청하는 B2B)와 각각의 결과를 정리했고, 사람이 B2B를 골랐다. 이 결정은 [ADR 0001](adr/0001-model-applications-as-b2b-org-requests.md)에 남겼다. 그 뒤로 이어진 설계가 모두 이 결정을 따른다.

- 신청자는 학생이 아니라 기관을 대표하는 성인(대개 교사)이다.
- 실제 FAQ의 "수업 희망일은 최소 3주 뒤" 규칙이 도메인 규칙이 되었다.
- 모호했던 "연락 가능 날짜 기준 자동 안내 메일"은 "담당자가 연락하는" 실제 흐름에 맞춰, 운영자가 전화하기 전에 메일로 먼저 연락을 열어 주는 자동화로 해석할 수 있었다.

과제 문구를 그대로 구현하는 대신 실제 서비스를 먼저 조사하게 한 것이 가장 큰 방향 전환이었다. 조사는 AI가 빨리 해냈지만, 어느 쪽으로 갈지는 과제의 의도와 실제 서비스를 둘 다 놓고 사람이 정했다.
